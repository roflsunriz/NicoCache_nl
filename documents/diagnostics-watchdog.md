# 常駐診断アプリと自動障害レポート

`NicoCacheDiagnostics.jar`は、NicoCache_nlとは別プロセスで常駐する診断GUIです。
起動管理GUI、タスクトレイ、ヘッドレスCLI、直JAR、自動起動のどの経路から
NicoCache_nlを起動しても、本体の共通エントリーポイントが診断アプリも自動起動します。
画面を利用できる場合はタスクトレイ、画面のない環境では
バックグラウンドで監視を継続します。診断アプリは監視と証拠採取だけを行い、
NicoCache_nlの自動再起動は行いません。

NicoCache_nl本体、起動管理ランチャー、診断アプリは別プロセスですが、本体と診断アプリの
正常な寿命は同期します。
常駐ランチャーがある状態で`NicoCacheLauncher.jar --headless --stop`を別プロセスから
実行した場合は、本体と診断アプリが通常停止し、ランチャーだけが残ります。本体がクラッシュ、
強制kill、JVM異常終了した場合は診断アプリが残り、障害採取を続けます。診断プロセスだけが
稼働中に終了した場合は、本体が再起動します。ランチャー画面の「ランチャーのみ終了」は
本体と診断アプリを停止しません。

## 監視内容

2秒ごとに次の2経路を確認します。

- ランダムトークンで認証されたループバック管理APIのハートビート
- NicoCache_nlの実際のプロキシー処理を通る`DEBUG`仮想ホストのハートビート

管理APIだけが応答する場合はプロキシー処理の停止、両方が応答しない場合はJVM全体の
停止候補として区別します。3回連続で失敗すると障害情報の採取を開始します。
直近300回、約10分間のハートビートは容量固定のメモリーリングへ保持するため、
通常時に監視履歴をディスクへ書き続けません。

本体の停止操作では、停止前に利用者データの
`data/nicocache-expected-stop.properties`へ対象PIDと時刻を記録します。
診断アプリはこのマーカーまたは本体の`stopping`状態を確認し、通常終了を障害として
記録しません。プロセス消滅、強制終了、ハートビート断だけを自動採取の対象にします。

## 障害時に収集する情報

障害検出後は自動再起動せず、次の情報を採取します。

- 障害の種類と直近のハートビート履歴
- OS、CPUアーキテクチャ、Java VM、メモリー、スレッド数
- アプリケーションJAR、設定、フィルター、Extension、証明書の存在とメタデータ
- `debug.log`、本体・診断ログ、直前のスレッドダンプの末尾最大1 MiB
- 検出直後、2秒後、5秒後のスレッドダンプ
- 取得できなかった項目とその理由

管理APIが応答する場合は本体内の`ThreadMXBean`から取得します。管理APIも停止している
場合は、同梱ランタイムの`jcmd`から対象PIDへ外部接続して、停止した本体を変更せずに
スレッドダンプを試みます。プロセスがすでに終了している場合は、取得できるログと
実行環境だけをレポートへ残します。

## レポートと機密情報

レポートは利用者データの
`diagnostics/incidents/<日時>-<障害種別>/report.html`へ、外部画像、外部CSS、
JavaScriptを含まない単一HTMLとして原子的に保存します。外部サーバーへの送信は
行いません。

保存前に次の情報を自動的に置換します。

- Authorization、Bearerトークン、Cookie、パスワード、APIキー
- アプリケーション、利用者データ、ホーム、テンポラリーディレクトリの絶対パス
- メールアドレスとループバック以外のIPアドレス
- 認証・署名・セッションに使われるURLクエリ値

同じメールアドレスやIPアドレスは、同一レポート内で同じ匿名IDになるため、関連する
ログ行を追跡できます。JKS、秘密鍵、Cookieの元値は収集しません。

特定動画だけで発生する不具合を識別できるよう、動画IDと動画タイトルは匿名化せず
保持します。レポートを第三者へ渡す場合は、この点を理解したうえで共有してください。

## GUIと手動収集

タスクトレイアイコンまたはウィンドウには、現在の状態、最終ハートビート、直近の
レポートを表示します。「今すぐ収集」は障害判定を待たず、同じ匿名化処理で手動レポートを
作成します。「レポートを開く」から保存先を表示できます。ウィンドウを閉じても
タスクトレイで監視を続けます。「診断アプリを終了」を選ぶと本体へ正常停止を要求し、
本体と診断アプリを揃って終了します。クラッシュ後に本体が存在しない場合は診断アプリだけを
終了します。

診断アプリだけを直接起動する場合は次を使用します。

```powershell
java -jar .\NicoCacheDiagnostics.jar
```

GUIのない環境で1回だけ採取する場合は、NicoCache_nlと同じアプリケーションルートで
次を実行します。常駐監視は行いません。

```powershell
java -jar .\NicoCacheDiagnostics.jar --collect-now
```

パッケージ版にはWindows用`NicoCacheDiagnostics.cmd`と、Linux/macOS用
`NicoCacheDiagnostics`も含まれます。

## 故障注入による実動作検証

リリース前のE2Eでは、通常の起動確認だけでなく、隔離したNicoCache_nlへ意図的に障害を
発生させ、次の製品経路を自動検証します。

- 正常稼働中は障害レポートを生成しない。
- 管理APIだけを3回連続で到達不能にすると、診断アプリが自動で1件のHTMLを生成する。
- 生存中の本体へ同梱`jcmd`で検出直後、2秒後、5秒後の3回接続し、各スレッドダンプを
  HTMLへ収録する。
- 本体を外部から強制終了すると`process-exited`レポートを自動生成し、本体を再起動しない。
- `--headless --stop`による計画停止では新しい障害レポートを生成せず、本体と診断アプリが
  揃って終了する。
- 本体の外部強制終了後は診断アプリが残り、直JARで本体を再起動した後の正常停止では
  両方が終了する。
- 偽のBearerトークン、Cookie、APIキー、メールアドレス、外部IP、個人パスがHTMLに残らず、
  動画IDと動画タイトルは残る。
- Windows配布アプリイメージでも、実際の同梱JREと`jcmd.exe`を使って3回のダンプを取得する。

これらは`test-e2e.ps1`と`packaging/windows/test-windows-app-image.ps1`で毎回再現できます。

ただし、診断アプリ自身が同時に強制終了した場合、OS全体の停止、電源断、保存先ディスクの
故障・容量枯渇・書き込み権限喪失では、新しいレポートを保存できません。本体プロセスが
すでに消滅した後はスレッドダンプを取得できないため、その場合は終了前のハートビート、
設定、ファイル構成、直近ログと取得失敗理由を保存します。

## 取得できない場合

- 本体が診断アプリの起動完了を10秒以内に確認できない場合は、監視されない本体を
  起動せずエラーを表示します。`data/logs/nicocache-diagnostics.log`を確認してください。
- 管理APIだけが失敗する場合は、利用者データの
  `data/nicocache-control.properties`が現在のプロセスのものか確認します。このファイルの
  トークンを表示または共有しないでください。
- 外部スレッドダンプが失敗する場合は、同梱`jre/bin/jcmd`の存在、対象プロセスと
  診断アプリを同じOS利用者が実行していることを確認します。
- 通常停止なのにレポートが生成された場合は、停止マーカーを書き込めない権限や
  読み取り専用の利用者データルートになっていないか確認します。
